The Unified Whole-Foods Database

A separate, unfinished successor to the food database the app ships with. What it is, what has been done, how far the app has moved since August, and what the merge now has to carry. Written so a session with no earlier context can pick it up.

Started 2026-08-10 · Brought current 2026-11-06, app version 1.0.83.2 · C:\Dev\lifestead-app\unified-database\

Two databases. Confirm which one is meant before touching either.

assets/data/foods_reference.db is the live one: the shipped app reads it, and a change forces a slow re-import on every phone. unified-database/unified_foods.sqlite is this project: lib/db.ts never reads it and no screen changes because of it. A session once spent hours translating the live file while the owner believed the unified one was being worked on, at a cost of about 8 hours. If anyone says "the new database" or "the other database" without naming a file, stop and ask.

Where it stands: this database has not changed since 2026-08-12. The app has changed a great deal, which is what this update records. Nothing here is urgent and no swap is scheduled.

Why this exists

The app's food data came from a one-time Python filter whose reasons for keeping or dropping any food were never captured as rules anybody could test or run again. This project rebuilds that work:

  • Nothing is discarded on the way in. Every source's full original record survives word for word, even after normalization.
  • Classification is a versioned, unit-tested rule engine, so every decision has a name, a reason and a test.
  • Cross-source matching uses evidence (species and Latin names, LanguaL codes) rather than fuzzy name guessing, so one food measured by two national agencies links correctly in any language.
  • Every automated call can be reviewed. A published tool lets a person confirm or correct classifications and matches at scale: the tool proposes, a person decides.

The end goal is a better-sourced, fully auditable database that takes over from the live one and carries forward what has been built on it: the scores for all 19 conditions, audit decisions, aliases, interaction rules and every recipe.

How the two databases link

Every live row except the 6 Derived ones finds its unified record today:

  • Eight sources: live food_id equals unified source_food_id.
  • Norway: live source_code equals unified source_food_id. Its food_id does not link.

The source name must be part of the join. Live source_code also matches other records by coincidence in France (542 rows) and Japan (375 rows), so a join that tries both columns picks up the wrong foods.

How the classification rules got this far

classify.js started from earlier keyword lists and went through about 15 rounds of refinement, from bug reports and from scans of random samples out of the review queue. The discipline throughout: every proposed fix is checked against every matching record in the database before being trusted. Two examples:

  • One branded soy-protein "kebab" wrongly classed as a whole food led to a family of gaps: gravy, stuffed and filled dishes, "meat alternative" phrasing, mycoprotein and branded meat analogs. About 200 records were corrected in one pass, each confirmed as wrong first.
  • A report that "Batavia, crue" had become "Batavia, flood" led to a scan of every machine-translated French name and 11 false-friend errors, where a French word has two meanings and the wrong one was picked. A correction mechanism now exists for that whole class.

The last change to the source data was adding 8,712 lycopene values on 2026-08-12; the last change to the database is the food_curation table on 2026-11-06. The full history of every round is in unified-database/README.md (over 1,700 lines), which remains the authoritative record; this page is an orientation.

Why this cannot break the live app

  • Isolation while it is being built. No import path and no shared runtime connect this folder to the app.
  • The export has to match the schema the bundled database uses, checked by an automated diff against every table lib/db.ts queries before any export is bundled.
  • Every existing decision gets an integrity check. Each food and source pair, score, alias, rule, recipe name and hidden flag must resolve against the candidate, or be a deliberate, traceable change. Nothing is dropped silently.
  • The swap replaces the reference file only. The re-import in lib/db.ts overwrites the bundled copy when the version stamp differs. The person's database, inside_story.db, is a separate file and is not touched.
  • Rolling back means shipping the previous file with a new version stamp, through a rebuild. It works, and it is not instant: phones reinstall.

Picking this up in a fresh session

  1. Confirm which database the owner means. Ask if a request does not name the file.
  2. Read unified-database/README.md in full for the dated history.
  3. Look at the data with sqlite3 -readonly. The tool is at C:\Users\TonyR\AppData\Local\Android\Sdk\platform-tools\sqlite3.exe.
  4. To confirm the environment, run these five, which stayed off the database on 2026-11-06: node pipeline/classify.test.js, match.test.js, ingest.test.js, apply-audit-decisions.test.js and apply-translation-corrections.test.js, from unified-database/. Do not run the ingest commands in the README's "Running what exists today" section just to test. They write to the database. init-db.js --force deletes it.
  5. Open the curation report before assuming anything about scope. It replaced the older review tool as the place to look.
  6. After any change to either database, run node scripts/backup_reference_dbs.js, and never git add either file.
  7. Re-ingesting the legacy sources needs ClaudeWork/unified_food_database_v3_full.sqlite.zip at the repo root. It was there on 2026-11-06.
